## 2. 运行基线：本来已具备的能力

### 2.1 SSH 密钥并非新配置

用户在较早阶段已经创建了 `C:\Users\Administrator\.ssh\id_ed25519_node05`（ED25519，带口令），并将相应公钥加入服务器用户 `dhr` 的 `~/.ssh/authorized_keys`。当时完成了如下验证：

- 本地公钥与服务器 `authorized_keys` 中条目的 SHA-256 指纹一致；
- 使用 `ssh -i ... -o IdentitiesOnly=yes dhr@210.45.127.28`，在输入私钥口令后成功登录；
- 远端返回主机名 `node05`；
- 上传目标为 `dhr@210.45.127.28:/data04/1/dhr/geo_ring_cloud_auto_upload`。

因此，“服务器没有配置公钥”或“这把私钥天然不可用”均与已知事实不符。

### 2.2 自动上传的认证设计

仪表盘的状态接口明确声明：

```json
{
  "credential_mode": "ssh-agent",
  "passphrase_stored": false
}
```

对应代码也明确要求私钥口令必须已在 `ssh-agent` 中解锁。上传器调用 Windows OpenSSH 的 `ssh` 和 `sftp` 时使用：

- `BatchMode=yes`：禁止运行时询问密码或私钥口令；
- `IdentitiesOnly=yes`：只尝试配置的身份文件；
- `-i <identity_file>`：指定上述 `id_ed25519_node05`；
- 连接超时参数。

这套设计的安全含义是：系统不保存私钥口令，也不会在后台弹出交互式密码框；代价是后台进程必须能访问一个允许其签名的 SSH Agent。

## 3. 本轮调试中出现的问题、处理与结果

### 3.1 控制台状态、进度与任务中心的问题

用户在本轮之前和本轮初期连续报告过以下表现：上传进度显示为 0、下载完成后上传百分比短暂从 100% 变成 0、状态显示“已完成”但最终清单/复核尚在进行、任务切换失败、`Failed to fetch`、历史批次过多使多任务中心臃肿、趋势图未生效或活动临时文件显示不完整。

这些问题不能都归因于同一个原因。已采取的代码性处理包括：

1. 将上传进度、服务器复核进度、实际字节数和速率作为独立状态字段暴露给前端；
2. 保留上传 ledger（`continuous_upload_ledger.jsonl`）以便续传时识别已完成文件；
3. 改善任务中心切换和“已消失的上传进程”的容错；
4. 调整仪表盘状态读取、趋势写入和队列快照的错误处理，避免一个运行时文件锁或状态异常使整个 `/api/status` 失败；

6. 增加/修正 FY4B 官方下载数据导入的命名、产品变量识别、上传进度和服务器校验展示。

### 3.2 仪表盘进程/后台运行方式的调整

为避免浏览器关闭、终端关闭或窗口闪现影响控制台，曾尝试将仪表盘作为 Windows 后台/计划任务运行，并新增一个 PowerShell 监督脚本 `geo_ring_cloud_dash.ps1`。该脚本的目标是：若仪表盘 HTTP 进程退出，只重启界面宿主，不删除卫星数据，也不修改上传 ledger。

这是一个合理但带来新认证边界的变更：原先从用户交互会话启动的程序和后来由后台计划任务启动的程序，不必然共享同一 SSH Agent 访问权。

本轮有一次检查曾错误地报告“本地 8765 未监听”。之后用户指出浏览器界面仍可访问，随后用 API 确认仪表盘确实在运行。该判断已被后续事实推翻。产生偏差的可能原因包括检查时进程重启窗口、会话/权限不同或检查方法不充分；未保留足够证据判定唯一原因。因此本文将它记录为**已纠正的错误诊断**，不把它当作故障根因。

### 3.3 当前阻断上传的直接错误

截至 2026-08-23T13:29（仪表盘状态时间），两个未完成批次均在上传前 SSH 预检阶段失败：

| 批次 | 上传进度 | 失败阶段 |
| --- | ---: | --- |
| `20241101_20241130_h9` | 39 / 1436（3.52%） | `checking_ssh_connection` 后失败 |
| `fy4b_20240901_20241231_clm` | 0 / 2734（0%） | `checking_ssh_connection` 后失败 |

两者保存的错误文本相同：

```text
sign_and_send_pubkey: signing failed for ED25519
"C:\\Users\\Administrator\\.ssh\\id_ed25519_node05" from agent: agent refused operation
dhr@210.45.127.28: Permission denied (publickey,password).
```

代码显示，上传器在进入文件传输前会先执行等价于 `ssh ... true` 的预检，并将此阶段标为 `checking_ssh_connection`。因此可以严谨地得出以下结论：

> 当前失败的直接原因是：运行上传器的进程无法让 SSH Agent 对现有 ED25519 私钥执行签名。它在开始 SFTP 传输之前就停止了。

这也解释了为何 H09 显示一部分文件已上传但后来停止：历史 ledger 和已完成计数仍被保留，新的续传进程却在建立 SSH 会话前失败。

### 3.4 对“服务器故障”“权限被收回”“SSH 已断开”的检查

对话/终端记录中完成过的检查包括：

1. 用现有密钥在交互式 Windows 会话中连续 SSH 测试成功，远端返回 `node05`；
2. `ssh-add` 在交互式会话中能列出该密钥；
3. 针对服务器端文件/目录的只读探测和小型 SFTP 诊断写入曾成功；
4. 大量其他批次已经得到上传 PASS 和服务器 SHA-256 复核 PASS。

这些证据否定了“服务器整体拒绝该用户”“网络完全不可达”“所有 SFTP 上传都不能工作”这三种广泛假设。

但它们**不能证明**后台任务使用的 Agent 一定可用。事实上，当前由本调试会话执行 `ssh-add -l` 也出现过 `Error connecting to agent: Permission denied`，而仪表盘 API 仍可响应；这再次显示 Agent 可用性具有会话/令牌上下文差异，不能仅凭某个窗口已经“解锁”就推及所有后台进程。

### 3.5 “新增免口令密钥”的建议及其更正

曾提出“创建一把专用、免口令的上传密钥”作为备选。该建议的目的，是绕过后台进程无法调用交互式 Agent 的问题；它**不是**因为旧密钥未配置，也不是已执行的修复。

该方案的风险是私钥在本机落盘时没有口令保护，即使可以在服务器端限制命令、来源或目录，仍会扩大本机密钥泄露风险。用户质疑后已明确更正：

- 当前现有密钥配置仍然有效；
- 不应把新增免口令密钥表述为必需；
- 未创建新密钥，未修改服务器 `authorized_keys`；
- 后续优先研究如何让现有口令保护密钥在需要的执行上下文中可用。

## 4. 根因分析：结论强度与未决问题

### 已证实

1. 失败发生在 SSH/SFTP 建连之前，而非 SHA-256 校验、远端文件写入或卫星文件格式检查阶段。
2. 失败消息明确来自本地 SSH Agent 拒绝私钥签名。
3. 现有密钥、服务器授权和 SFTP 上传通道曾经成功工作。
4. 上传器不存储私钥口令，并明确依赖 SSH Agent。
5. 已完成文件会通过 ledger/完成计数保留；设计目标是不重复上传已确认完成的文件。
6. 本轮没有自动删除卫星原始数据；仪表盘状态的 `automatic_delete` 为 `false`。

### 有证据支持、但尚未完成受控验证的推断

最符合现有证据的架构性解释是：**仪表盘/上传器切换到 Windows 后台或计划任务运行后，其安全会话无法复用用户交互登录会话中已解锁的 SSH Agent，或 Agent 仅拒绝该后台令牌的签名请求。**

这一推断与“交互式 SSH 成功、后台上传器报 `agent refused operation`”一致，也符合 Windows 服务、计划任务和交互式用户会话之间经常不共享 Agent 授权的行为。它仍不是唯一被数学证明的原因：还需在同一用户、同一密钥、不同启动方式下记录 Agent 可见性和 `ssh ... true` 结果，才能把“会话隔离”升级为完全证实的根因。

### 已排除或缺乏证据的猜测

| 猜测 | 当前判定 | 理由 |
| --- | --- | --- |
| 服务器整体禁止上传 | 基本排除 | 多个批次上传和服务器复核 PASS，小型 SFTP 探测成功。 |
| `authorized_keys` 被删除或密钥不匹配 | 基本排除 | 历史指纹一致且交互式登录成功。 |
| 并行下载/上传直接导致 `agent refused operation` | 无证据 | 并发可能影响带宽和磁盘，但不能直接解释 Agent 拒绝签名。 |
| 服务器端 SHA-256 复核太慢导致本次失败 | 排除为直接原因 | 失败在 SSH 预检阶段，尚未传输或进入复核。 |
| 用户没有配置 SSH 密钥 | 错误 | 已完成密钥配置和成功登录。 |
| 必须新建免口令密钥 | 错误 | 仅为有安全代价的备选，现有密钥可在交互式会话中工作。 |

## 6. 建议的后续处置顺序（尚未执行）

1. **先做最小受控认证试验**：不启动上传、不改服务器、不产生卫星数据写入；分别从交互式会话和当前后台启动方式运行相同的 `ssh -o BatchMode=yes -o IdentitiesOnly=yes -i <existing-key> ... true`，记录退出码与 Agent 可见性。
2. **根据试验结果修复启动架构**：目标是继续使用现有口令保护密钥。优先方案是让上传进程在拥有该 Agent 授权的用户交互会话中受控启动，或采用 Windows 支持的、可审计的用户级 Agent 访问方式。
3. **只在认证预检通过后恢复上传**：H09 必须复用现有 ledger；FY4B 使用现有 manifest。不得因重启覆盖状态、重置进度或删除本地文件。
4. **上传完成后异步服务器复核**：保持 SHA-256 校验；校验进度应独立显示。下一批下载/上传的调度可以与复核并行，但必须受磁盘门禁、网络负载和上传 ledger 保护。
5. **观察而非盲目重试**：恢复后以 30 分钟周期监控状态；发现新的 `agent refused operation`、进程异常退出或复核失败时，先保存完整错误证据，再作针对性修复。

## 7. 对后续开发的约束

- 不再仅凭 UI 上的“运行/完成”文字判断真实状态；同时核对 PID、状态 JSON、ledger、服务器复核报告和 API 返回。
- 将“前端进程存活”“上传器进程存活”“SSH Agent 可签名”“服务器端可写”“服务器复核完成”建模为不同状态，避免一个“上传失败”掩盖真正的故障位置。
- 对仪表盘服务重启必须在运行记录中注明启动上下文；不得再把“端口检查一次失败”直接表述为“仪表盘未运行”。
- 未经用户明确同意，不创建免口令密钥、不改变服务器授权策略、不自动删除任何原始卫星数据。
- 对所有修复先增加或更新回归测试，并从干净提交启动长期下载/上传任务；当前工作区仍有未提交的控制台相关改动，不能把其行为描述成已发布的稳定版本。

## 8. 文档结论

本轮最关键的发现不是服务器存储或 SHA-256 校验，而是**自动上传的身份认证依赖 SSH Agent，而后台运行方式改变后该 Agent 对上传进程拒绝签名**。已有证据显示旧密钥和服务器权限此前有效；“重新配密钥”或“服务器坏了”不是严谨结论。

下一步应以受控的、只做认证预检的实验确认后台会话与 Agent 的关系，再恢复两个失败批次的断点续传。只有在现有密钥无法通过可审计方式服务于后台流程时，才应讨论新的受限专用密钥，并单独评估其安全代价。
